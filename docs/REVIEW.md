# Review and Alternatives

Status: independent review of the 1.0 foundation set, written after reading all sixteen documents and checking the main 2026 research citations. The documents themselves are unchanged. This file records the objections, the alternatives worth weighing and the decisions that should be settled before M0.

The review is deliberately adversarial. It is not a rewrite and it does not replace any rule in the specification.

## What the specification gets right

- The trust model is the strongest part. Separating translation from verification, assigning an evidence class per item and forbidding claims stronger than the evidence are the right foundations for a product sold to auditors.
- The tier model gives the project an honest answer for code it cannot prove: keep it in C/C++ behind an FFI stub rather than guessing. That is the correct default for a migration tool.
- Determinism, conservatism, locality of failure and explainability are stated as system-wide rules rather than as stage-local preferences.
- The C ABI boundary is the right first interop target. It is stable, toolchain-independent and testable in both directions.
- The worked examples make the rules concrete. They are the right seed for the golden-test suite.

## Objections

### 1. T2 changes behavior on programs that were not undefined

Document 06 presents T2 as memory-safe because violations of the original aliasing discipline become panics. But C++ permits aliasing that Rust's runtime checks reject without the original program having undefined behavior. A `RefCell` double borrow panics; an `Rc` cycle leaks. Both are observable changes. Example 5 avoids the problem only because `i32` is `Copy`.

This conflicts with G1 (correctness first). A runtime-checked tier is a behavior-changing tier. Either make T2 opt-in per project, default to a T1 arena or T3 contained unsafe when defined aliasing must be preserved, or state plainly that T2 is chosen only when the project accepts panic-on-alias as a defined outcome.

### 2. T0 rests on a Likely fact

Document 05 section 1.3 says zero-cost strategies require `Proven` or `Assumed`-by-contract facts; `Likely` facts may drive T1/T2. Example 2 emits `&[i32]` from `Likely NonNull` based on three observed call sites.

In whole-program mode that evidence can be promoted to `Proven`. In library mode it cannot: an external caller may pass null. Fix either the rule or the example, and require a contract or an `Option` at public boundaries.

### 3. Wall-clock solver timeouts defeat determinism

Document 03 forbids clock-dependent output. Document 09 exposes `solver_timeout_ms`, and the fallback tier depends on whether the solver returned `unknown`. A faster or slower run can therefore change the generated bytes.

Use a deterministic resource budget where the solver supports one, and fix the fallback for budget exhaustion so that elapsed time cannot select a tier. Record the budget in the report. If a wall-clock limit remains, the determinism claim must be narrowed.

### 4. C++ destruction order is specified incorrectly

Rust drops struct fields in declaration order. C++ destroys members in reverse declaration order. A custom `Drop` implementation runs before the fields are dropped and cannot reorder them without `ManuallyDrop` and explicit drops. The claim in document 06 section 5.2 that `impl Drop` preserves reverse order is not implementable as written.

Either emit `ManuallyDrop` fields and drop them in reverse order with explicit code, or document the order difference and verify it. Constructor member-initializer order has a related error: C++ initializes members in declaration order, not in the order written in the initializer list.

### 5. `new T[n]` is not equivalent to `vec![T::default(); n]`

For a non-trivial `T`, `vec![T::default(); n]` constructs one default value and clones it n times. It does not run n default constructors, so side effects, identities and invariants differ. It also fails for non-`Clone` types. Generate a per-element initialization loop and distinguish trivial from non-trivial construction.

### 6. Public multi-evaluation macros cannot become functions

Document 05 converts `FnExprMultiEval` macros to functions when arguments are side-effect-free at all observed call sites. A header macro has no linkage: future or external code can call `CLAMP(i++, 0, 10)` and rely on multiple evaluation. Keep a publicly visible multi-evaluation macro as a macro. A function is only safe for a private or whole-program macro whose call sites are all known.

### 7. T4 stubs for C++ signatures are under-specified

Document 06 says a flagged function gets a Rust stub with the signature the translation would otherwise have produced, implemented over an `extern "C"` wrapper. A C-ABI wrapper cannot pass `std::string`, `std::vector`, references or class values by value. Document 08 has marshalling conventions for pointers, strings and opaque handles, but the T4 section does not require them.

Either lower the signature to C-compatible types before generating the stub, or restrict T4 to C-compatible APIs and state the restriction. Otherwise the fallback fails exactly where C++ code is hardest.

### 8. IDs, configuration atoms and macro tokens have representation gaps

`NodeId = (ItemId, ordinal)` changes when any earlier node is edited, which breaks incremental caches and explanation links. Clang USRs are not guaranteed stable across Clang versions. Use content-addressed IDs or accept that caches and links are invalidated by edits.

`ConfigCondition` is a boolean formula, but value atoms such as `VERSION >= 3` need arithmetic and comparison theory. Define atoms as propositions, or solve the condition with a theory that understands their values.

`MacroFrame` stores argument spans, not token spellings. That is insufficient for `#` and `##`, and for tokens synthesized by macro expansion. Store token text or a synthetic-token representation.

### 9. Several standard-library mappings are research-grade

The mapping table marks the following as specified, but each needs a conformance suite before that claim is honest: `printf` return values, `%n`, locale decimal separators and `snprintf` truncation; iostream formatting state; stateful `std::map` comparators and equivalent keys; generic `std::atomic<T>`; `std::thread` detach and join lifetimes; `std::vector<bool>`. `cformat` is a good start, not a complete answer.

Downgrade the status of these rows and list the unsupported cases explicitly. A mapping that is guessed silently is worse than one that is flagged.

### 10. Verification and roadmap claims exceed the evidence

L7 shadow instrumentation for arbitrary C/C++ is a research project in its own right. "Zero false accepts" is measured by a mutation suite, not proved. M1 is L0 minus heap, strings and I/O, but is labeled L0; L0 includes `malloc`, `char*` strings and `printf`. M2's cJSON target of 70% at T0/T1 and 100% differential agreement has no supporting measurement.

Narrow the M1 and M2 exit criteria to what the milestone actually builds, and publish measurements before committing to M6 and M7.

### 11. The product needs a beachhead

Full C++ L3 plus templates, exceptions, interop, verification and V5 is a multi-year program. The risk register names well-funded competitors but does not choose a segment. A C99/C11 library beachhead in embedded or security-sensitive code would exercise the trust story without paying the C++ complexity cost first.

The verifier may also be the better standalone product: it can validate output from C2Rust, an LLM pipeline or a manual rewrite. The verifier is the durable asset; the full translator is the expensive one.

### 12. Licensing, qualification and security need decisions now

The repository is public Apache-2.0 while Q-08 leaves licensing open. Decide before accepting outside contributors.

Regulated customers need tool-qualification evidence (ISO 26262, DO-178C, IEC 62304), not only a differential report. M10 defers that entirely. If regulated buyers are the market, add a qualification workstream or a partner.

The exporter parses untrusted code outside the sandbox. Clang parser denial of service and parser vulnerabilities are not in the risk register. Add resource limits and sandboxing for the exporter, and move supply-chain checks earlier.

## Alternatives worth weighing

| Area         | Alternative                                                    | Trade-off                                                            |
| ------------ | -------------------------------------------------------------- | -------------------------------------------------------------------- |
| First scope  | C99/C11 libraries first, C++ later                             | Smaller surface, faster evidence, smaller market                     |
| Product      | Standalone verifier for any C-to-Rust output                   | Reuses the moat, decouples from translation quality                  |
| Product      | Contract-first migration workbench with human review           | Slower per module, more usable on real code                          |
| Analysis     | Datalog or abstract interpretation for points-to and ownership | Different precision and engineering cost than a boolean SAT encoding |
| Analysis     | Reuse Crown's ownership analysis for C, then extend            | Faster start, dependency on research code and assumptions            |
| Tiers        | Arena-first for graphs; T2 opt-in                              | Preserves defined aliasing better than `RefCell`                     |
| Verification | Translation validation for selected functions                  | Stronger than fuzzing where it applies, limited scope                |
| Verification | Link-swap as the primary library evidence                      | Uses the customer's own tests, needs interop early                   |
| AI           | Non-core proposer for contracts, tests and triage              | Reduces human cost without touching the trust path                   |
| Interop      | C ABI with opaque handles                                      | Less ergonomic than `cxx`, much broader and more stable              |

## Decisions to settle before M0

| Decision             | Recommendation                                    | Reason                                                                   |
| -------------------- | ------------------------------------------------- | ------------------------------------------------------------------------ |
| First release scope  | C99/C11 libraries, embedded or security-sensitive | Prove the trust story before C++ complexity                              |
| T2 policy            | Opt-in; report it as a semantic change            | Panics on defined aliasing are not correctness-preserving                |
| T0 confidence        | `Proven` or contract only                         | A `Likely` fact cannot justify a non-null reference at a public boundary |
| Solver budget        | Deterministic budget, fixed fallback              | Preserve byte-identical output                                           |
| C++ drop order       | `ManuallyDrop` or a documented difference         | Rust field order is declaration order                                    |
| Public macros        | Preserve multi-evaluation macros                  | External call sites are unknown                                          |
| T4 C++ signatures    | Lower to C-compatible or restrict T4              | C ABI cannot carry arbitrary C++ types                                   |
| Node identity        | Content-addressed IDs                             | Editing a body should not invalidate unrelated explanations              |
| Licensing            | Decide before contributors arrive                 | The repository is already public Apache-2.0                              |
| Verification product | Evaluate a standalone verifier                    | It may be the stronger commercial wedge                                  |

## What this review does not do

It does not change the specification, resolve the open questions, or claim that the objections are fatal. It records them so that the first implementation decisions are made deliberately rather than inherited by accident.
