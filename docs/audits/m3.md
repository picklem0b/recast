# M3 Audit

M3 is the verification-and-gate milestone. Its exit criteria in [`project/roadmap.md`](../project/roadmap.md) are met at `v1.3.14`: the mutation threshold holds on the M2 corpus, a report passes schema validation with its limitations statement, the determinism check runs on the corpus, and `recast run` is the documented workflow. This page records each build point, what it covers, what it refuses, and the evidence for the claims it makes; build items outside the exit criteria that remain are listed at the end.

## Scope

Document 11 defines M3 as: V3 differential fuzzing, V4 sanitizer and Miri integration, a sandbox runner, link-swap machinery stubs, the safety gate with profiles and rules, the `recast-report/1` schema with `report.md` and SARIF, evidence classes and the claim-language lint, the `verify`, `run`, `gate`, `report`, `explain` and `diff` commands, a mutation-testing harness and frozen `/1` schemas.

## What the report records

`recast-report/1` is owned by `recast-report`; assembly is in `recast-orchestrator`. A report has:

- A fixed key order and a sorted `items` array; `Report::validate` rejects an unknown schema, an empty or duplicate item id, an unknown tier, rung or evidence class, and an unsorted item list.
- `run` identity: tool version, the hash of `recast_analysis::RULE_SET`, schema versions, source and config hashes, the target, the profile, a UTC start time and the machine.
- `determinism`: `recast verify` compares the crate it compiled with a fresh translation from the same TIR (`runs: 2`). The report is rendered after that comparison and is deterministic by construction. This covers the generated crate, not the tier map or explanation records, because neither exists yet.
- One `items` entry per function with a body: source span, generated path, tier T0, verdict, evidence class and per-rung evidence. The differential contributes one V2 entry per function that a case calls, and one per function that a sweep exercises. V1 and V4 contribute a pass or fail entry to every item, and V3 one per function the fuzzer called with the execution count and seed. A rung that did not run is listed in `skipped_rungs`, never as evidence.
- `findings` from `recast-analysis` and, for `UB-001`, `UB-007` and `UB-008`, `ub_sites` with the original behavior, the translated behavior and the configured policy. V1 and V4 notes that need human attention are carried as `TOOL:V1` and `TOOL:V4` findings.
- `summary.mutation` when operator mutation ran: generated, killed and surviving mutants, the kill rate, the per-rung behavioral kill counts (`v2-calls`, `v2-sweeps`, `v3-fuzz`), `killed_by_compile` for mutants the build rejected, and `killed_by_check` for behavioral kills that were a panic or a timeout under the checked build rather than a wrong value. The three add up to `killed`; a build rejection is a kill but not behavioral evidence. `report.md` renders the kill rate, the per-rung figures and the build rejections in its key-numbers table.
- `report.md` always ends with the verbatim limitations statement; a report with no limitations section fails its own rendering test. `report.sarif` carries every finding as SARIF 2.1.0.

The evidence vocabulary in this build:

| Class | When it is assigned                                                                     |
| ----- | --------------------------------------------------------------------------------------- |
| `E0`  | The crate does not compile, a check failed, or no rung supplied evidence for the item.  |
| `E1`  | V1 hygiene passed, but no call, sweep or fuzz input exercised the function.             |
| `E2`  | The differential (calls, a sweep, or both) exercised the function and passed.           |
| `E3`  | V2 passed and every V3 fuzz input for the function passed.                              |
| `E4`  | V3 passed and the V4 checks passed.                                                     |

`E5` is not assigned: V5 is not enabled. A skipped rung is listed, never folded into a stronger class.

### What V1, V3 and V4 check

- **V1** runs `cargo clippy --offline` with the deny-list from document 07 section 3.2 (`clippy::correctness`, `clippy::suspicious` and `clippy::perf`) on the generated crate, counts every `unsafe` token (which must be zero because the crate forbids unsafe code), inventories `#[repr(C)]` types and their layout assertions, and rejects the patterns `static mut`, `transmute`, `from_raw_parts` and `.unwrap()` in generated code. Style lints are allowed, as the document specifies. The inventory reads the generated source as text; the translator emits a controlled subset, so this is exact for that subset rather than a syntax-tree pass.
- **V3** mutates the arguments of the calls a case already defines, decoded from each parameter's TIR type: an array keeps its length, a record keeps its fields and a string keeps its terminator. The seed and generated corpus are written to `recast-out/verify/v3/` and the report records the seed and execution count. This is deterministic mutation fuzzing, not coverage-guided fuzzing.
- **V4** compiles the original C driver with UBSan, and with ASan when an ASan probe can start on the host; the translated drivers already run with overflow checks and debug assertions. An unavailable ASan is a note, not a pass. Miri gets a test target: the generated library is copied under `verify/v4/miri/crate` with one test per V2 call using the same argument setup, and `cargo miri test` runs it in the sandbox when the toolchain provides Miri. A failing test, an undefined-behavior report or a timeout fails V4; a missing `cargo miri` is a note, never a pass. The generated crate is not modified, so V1 and mutation testing still see only the translation.

### Assumptions

A pointer or slice parameter is recorded as assumption `PTR-001` ("non-null and points at live storage"). It names `V2` as the verifying rung when a call, sweep or fuzz input exercised the function. An unexercised function leaves `verified_by` empty, so the gate reports it under GATE-006.

### Determinism

GATE-005 compares the generated crate on disk with a second translation from the same TIR. A stale crate, a nondeterministic translator or a write that differs from the translation both fail the check. Wall-clock fields, the environment and the report's own start time are excluded from the compared bytes.

## What the gate evaluates

`recast gate` reads `report.json`, re-evaluates it under a profile and writes `verify/gate.json`. It does not translate, compile or execute anything.

| Rule       | Evaluation in this build                                                                                                     |
| ---------- | ---------------------------------------------------------------------------------------------------------------------------- |
| GATE-001   | The generated crate carries `#![forbid(unsafe_code)]`; the report must list no `unsafe` block and no generated count.          |
| GATE-002   | Every recorded `unsafe` block needs a SAFETY comment and a test; with no blocks the rule passes.                              |
| GATE-003   | Every T4 stub needs a passing V2 boundary test and a profile that allows T4; with no stubs the rule passes.                   |
| GATE-004   | A rejected item needs a T4 fallback; otherwise the rule fails.                                                               |
| GATE-005   | Two translations must be byte-identical.                                                                                     |
| GATE-006   | Assumptions without `verified_by` fail `strict` and are a note elsewhere.                                                    |
| GATE-007   | Every UB site names both the original and translated behavior.                                                               |
| GATE-008   | Not applicable: no exported FFI types and no layout inventory exist yet. The generated `#[repr(C)]` asserts are enforced by V0. |
| GATE-009   | The report records the environment and at least one toolchain version.                                                       |
| PROFILE-001 | The highest item tier must not exceed the profile maximum.                                                                  |
| PROFILE-002 | T3 items require `allow_t3`.                                                                                                 |
| PROFILE-003 | T4 items require `allow_t4`.                                                                                                 |
| PROFILE-004 | Every rung the profile requires must have a passing result.                                                                  |
| PROFILE-005 | Unexercised items are a note in `standard`, `permissive` and `audit`, and a failure in `strict`.                             |
| PROFILE-006 | UB sites are listed for human review; the gate does not yet select T4 for them.                                              |

`audit` runs every rule but never returns REJECT: a failure is reported and the verdict becomes ACCEPT_WITH_NOTES. `strict` and `standard` enforce every rule.

### Current gate behaviour

`standard` requires V0, V1, V2 and V4. All four now exist, so a standard run over a translated case reaches `ACCEPT_WITH_NOTES` when the only failures are note-disposition rules: unexercised functions, an unverified pointer assumption or a skipped V3. `strict` turns those notes into failures, so the same run is REJECT under `strict`. V3 and V5 are not required by `standard`. `verify` still defaults to the `audit` profile so that a measurement can be produced without a decision; `run` uses the configured profile, and `gate` defaults to `standard`, or to `[gate] profile` in `recast.toml`, and accepts `--profile` for a re-evaluation.

### The user surface

- `recast run` is `translate`, `verify` and `gate`, in that order. It exits non-zero at or below `--fail-on` (default `REJECT`) and stops on a determinism failure.
- `recast explain <item>` reads `report/report.json` and prints the item's source span, tier, evidence class, verdict, per-rung evidence, assumptions, notes and findings. `--format json` prints the item and its findings as one object.
- `recast diff <before> <after>` compares two reports and names tier changes, evidence-class changes, new and resolved findings, and verdict changes. `--format json` emits the same comparison as an object.
- `recast report` re-renders `report.md` and `report.sarif` from `report.json`. Rendering runs the claim-language lint; a phrase the evidence does not support fails the command instead of reaching a reader.

## Non-claims

- C++ input is not translated at this build point. The refusal is deliberate: `int &r` read as C would lose the write-back, and classes, overloads and templates have no lowering until M6. A C++ source, and a database that lists both languages, fails with exit code 3 and the reason, and writes no AST for any unit in it.
- M2 exit criteria remain open. The report covers the subset the current translator accepts; its coverage figure is within that subset, not cJSON.
- The translation emits T0 only. The tier rules in a profile are implemented and unit-tested, but no T1 to T4 item exists to exercise them.
- V1's unsafe and layout inventories read generated text, not a syntax tree. They are exact for the translator's controlled subset, not for arbitrary Rust.
- V3 is deterministic mutation fuzzing seeded from the case's calls. It has no coverage feedback and makes no claim about unexecuted paths.
- ASan is evidence only when the host can start it; an ASan failure to start is recorded as a note. Miri is evidence only when the host toolchain provides `cargo miri`; the build host does not, so V4 records a note and no Miri pass is claimed. The target exercises the calls V2 executed, not paths those inputs do not reach.
- The sandbox uses a scratch directory, a cleared environment for compiled programs (Cargo checks keep the toolchain variables they need), CPU, memory and file-size limits, and a timeout. It does not isolate the network or mounts; a container runtime would be needed for that, and the report says so.
- The report's determinism check covers the generated crate only. It is not the full GATE-005 hash set.
- The gate does not repair anything. There is no T4 regeneration path yet.
- The mutation claim covers the M2 corpus at this build point and the operator mutations the harness generates. It is not a claim about the full mutation suite in document 10 section 5 (tier flips, dropped wrapping operations, reordered destruction) or about a larger corpus.
- Four of the 62 kills are mutants the build rejected, not V2 to V4 evidence; they are reported under `killed_by_compile`. Of the 58 mutants that built, all 58 were killed behaviorally, so the 98% threshold holds on either denominator.
