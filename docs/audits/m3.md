M3 is the verification-and-gate milestone. It is **in progress**: the exit criteria in [`project/roadmap.md`](../project/roadmap.md) are not met, and this page records each build point, what it covers, what it refuses, and the evidence for the claims it makes.

## Scope

Document 11 defines M3 as: V3 differential fuzzing, V4 sanitizer and Miri integration, a sandbox runner, link-swap machinery stubs, the safety gate with profiles and rules, the `recast-report/1` schema with `report.md` and SARIF, evidence classes and the claim-language lint, the `verify`, `run`, `gate`, `report`, `explain` and `diff` commands, a mutation-testing harness and frozen `/1` schemas.

## What the report records

`recast-report/1` is owned by `recast-report`; assembly is in `recast-orchestrator`. A report has:

- A fixed key order and a sorted `items` array; `Report::validate` rejects an unknown schema, an empty or duplicate item id, an unknown tier, rung or evidence class, and an unsorted item list.
- `run` identity: tool version, the hash of `recast_analysis::RULE_SET`, schema versions, source and config hashes, the target, the profile, a UTC start time and the machine.
- `determinism`: `recast verify` compares the crate it compiled with a fresh translation from the same TIR (`runs: 2`). The report is rendered after that comparison and is deterministic by construction. This covers the generated crate, not the tier map or explanation records, because neither exists yet.
- One `items` entry per function with a body: source span, generated path, tier T0, verdict, evidence class and per-rung evidence. The differential contributes one V2 entry per function that a case calls, and one per function that a sweep exercises, with the execution count and, for a sweep, the shared seed and execution budget.
- `findings` from `recast-analysis` and, for `UB-001`, `UB-007` and `UB-008`, `ub_sites` with the original behavior, the translated behavior and the configured policy.
- `skipped_rungs` V1, V3, V4 and V5 with the reason each did not run.
- `report.md` always ends with the verbatim limitations statement; a report with no limitations section fails its own rendering test.

The evidence vocabulary in this build is deliberately small:

| Class | When it is assigned                                                        |
| ----- | -------------------------------------------------------------------------- |
| `E0`  | The crate compiles, but no call or sweep exercised the function, or an item failed. |
| `E2`  | The differential (calls, a sweep, or both) exercised the function and passed. |

`E1` is not assigned: V1 static hygiene is not built. `E3` to `E5` are not assigned: V3, V4 and V5 are not built. A skipped rung is listed, never folded into a stronger class.

### Assumptions

A pointer or slice parameter is recorded as assumption `PTR-001` ("non-null and points at live storage"). It names `V2` as the verifying rung when a call or sweep exercised the function. An unexercised function leaves `verified_by` empty, so the gate reports it under GATE-006.

### Determinism

GATE-005 compares the generated crate on disk with a second translation from the same TIR. A stale crate, a nondeterministic translator or a write that differs from the translation both fail the check. Wall-clock fields, the environment and the report's own start time are excluded from the compared bytes.

## What the gate evaluates

`recast gate` reads `report.json`, re-evaluates it under a profile and writes `verify/gate.json`. It does not translate, compile or execute anything.

| Rule       | Evaluation in this build                                                                                                     |
| ---------- | ---------------------------------------------------------------------------------------------------------------------------- |
| GATE-001   | The generated crate carries `#![forbid(unsafe_code)]`; the report must list no `unsafe` block and no generated count.          |
| GATE-002   | Every recorded `unsafe` block needs a SAFETY comment and a test; with no blocks the rule passes.                              |
| GATE-003   | Every T4 stub needs a passing V2 boundary test and a profile that allows T4; with no stubs the rule passes.                   |
| GATE-004   | A rejected item needs a T4 fallback; otherwise the rule fails.                                                               |
| GATE-005   | Two translations must be byte-identical.                                                                                     |
| GATE-006   | Assumptions without `verified_by` fail `strict` and are a note elsewhere.                                                    |
| GATE-007   | Every UB site names both the original and translated behavior.                                                               |
| GATE-008   | Not applicable: no exported FFI types and no layout inventory exist yet. The generated `#[repr(C)]` asserts are enforced by V0. |
| GATE-009   | The report records the environment and at least one toolchain version.                                                       |
| PROFILE-001 | The highest item tier must not exceed the profile maximum.                                                                  |
| PROFILE-002 | T3 items require `allow_t3`.                                                                                                 |
| PROFILE-003 | T4 items require `allow_t4`.                                                                                                 |
| PROFILE-004 | Every rung the profile requires must have a passing result.                                                                  |
| PROFILE-005 | Unexercised items are a note in `standard`, `permissive` and `audit`, and a failure in `strict`.                             |
| PROFILE-006 | UB sites are listed for human review; the gate does not yet select T4 for them.                                              |

`audit` runs every rule but never returns REJECT: a failure is reported and the verdict becomes ACCEPT_WITH_NOTES. `strict` and `standard` enforce every rule.

### Current gate behaviour

`standard` requires V0, V1, V2 and V4. V1 and V4 are not built, so `standard` **rejects every run in this build**. That is the correct answer from the gate, not a defect: the evidence a standard run needs does not exist yet. `verify` therefore defaults to the `audit` profile so it can produce a measurement without pretending to a decision. `gate` defaults to `standard`, or to `[gate] profile` in `recast.toml`, and accepts `--profile` for a re-evaluation. `recast gate` on a current report names V1 and V4 as missing.

## Remaining M3 work

- V1 static hygiene: clippy deny-list, a syntax-tree unsafe inventory, layout-assert inventory and forbidden-pattern checks.
- V3 differential fuzzing: a structure-aware decoder from TIR types, a recorded seed corpus and RNG seed, an execution budget and divergence triage.
- V4: ASan/UBSan on the original, overflow-checked and Miri runs on the translated crate, and a sandbox runner.
- `recast run`: one command over translate, verify and gate, with `--fail-on` and the documented default workflow.
- SARIF, `explain`, `diff`, the claim-language lint and a CI check over generated prose.
- A repository-wide mutation harness at the 98% M3 threshold; the per-case harness exists and the M1 corpus kills 108 of 108 at V2.
- Link-swap stubs and the T4 fallback path, which need the interop work in M5.
- Freezing `recast-ast/1`, `tir/1` and `recast-report/1` with a round-trip check per schema.
- The M3 exit criteria: mutation kill rate at least 98% across V2 to V4 on the M2 corpus, a schema-valid report with the limitations statement, a working GATE-005 on the corpus, and `recast run` as the documented workflow.

## Non-claims

- M2 exit criteria remain open. The report covers the subset the current translator accepts; its coverage figure is within that subset, not cJSON.
- The translation emits T0 only. The tier rules in a profile are implemented and unit-tested, but no T1 to T4 item exists to exercise them.
- The report's determinism check covers the generated crate only, as stated above. It is not the full GATE-005 hash set from document 07 section 8.
- The gate does not repair anything. There is no T4 regeneration path yet.
- No performance or mutation-threshold claim beyond the M1 corpus is made.
